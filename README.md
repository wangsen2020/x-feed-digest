# X Feed Digest

定时汇总你关注的博主当日发的帖子，在本地整理成候选列表。自用工具，不分发。

## 它是怎么拿数据的

不抓 DOM。x.com 前端自己是通过 GraphQL 取数据的，这个扩展做两件事：

1. **嗅探模板**（`src/net-hook.js`，MAIN world / document_start）
   拦截 X 自己发出的 `UserTweets` / `UserByScreenName` 等请求，把 `queryId`、
   `features`、`fieldToggles`、`variables` 和必要的请求头原样存下来。

2. **复用模板**（`src/xapi.js`）
   service worker 里用存下来的模板重新发请求，只替换 `variables` 里的
   `userId` / `screen_name` / `count`。Cookie 由浏览器自动带上。

这么做的好处是**不需要打开任何标签页**，也就不受后台标签页渲染挂起的影响
（X 的时间线是虚拟列表，后台标签页里滚动是拿不到新节点的）。X 前端发版后
`queryId` 会变，但只要你正常刷一次 x.com，模板就自动更新了。

`src/parse.js` 用深度遍历找推文节点（`__typename === 'Tweet'`），不依赖
固定路径，对响应结构调整免疫。

## 失败处理

模板从来没捕获过（`setup`）和 X 发版导致模板过期（`stale`）是两回事：
前者扩展能**自己开后台页面补上**，后者才需要你去刷 x.com。所以它们分成了
不同的错误类型，提示文案和按钮行为都不一样——把前者说成「X 前端发版」是误导。

| 状态码 | 判定 | 行为 |
|---|---|---|
| —（本地） | 模板未捕获 | 「自动捕获一次」：后台开页走一遍就好，无需你操作 |
| 401 / 403 | 凭证失效 | 红色角标 + 常驻通知「打开 x.com 重新捕获」，点击直接开标签页 |
| 404 / 400 | queryId 或 features 过期 | 同上，文案为「接口版本已变更」 |
| 429 | 限流 | 静默退避，连续 3 次才提醒 |
| 5xx / 网络 | | 静默，连续 3 次才提醒 |

重新捕获成功后角标自动清除，并弹一条「已恢复」提示。

另有**被动缓存池**兜底：你平时刷 X 时，扩展会把看到的推文顺手存 3 天。
主动抓取全部失败时会自动改用缓存池的数据，界面上会标注「来自本地缓存」。

## 安装

Chrome → 扩展程序 → 打开开发者模式 → 加载已解压的扩展程序 → 选这个目录。

## 第一次使用

1. 打开 x.com，**访问任意一个博主的主页**（捕获时间线模板），
   再打开一次自己的**「正在关注」**页面（捕获 `Following` 模板）。
2. 点扩展图标 → 打开汇总面板 → **「从我的关注列表导入」**，名单自动填好。
3. 点「立即汇总一次」，看诊断区和结果区。

诊断区会明确告诉你哪个模板还没捕获到。

## 实测结论（2026-09-16，Chrome 153）

用真实登录态验证过三件事：

1. **博主主页的 operation 已经从 `UserTweets` 换成 `UserOriginalsTimeline`**。
   硬编码 operation 名的写法早就失效了——这正是「存模板而不是存常量」的价值。
   代码里按 `UserOriginalsTimeline → UserTweets → UserTweetsAndReplies` 的
   优先级挨个试，哪个捕到用哪个。
2. **复用请求可行**：重放 `UserOriginalsTimeline` 返回 200，解析出 37 个推文节点。
3. **不需要 `x-client-transaction-id`**。重放时完全没带这个头也照样通过，
   所以 `xapi.js` 现在会主动把它删掉——带着过期值反而更容易被拒。
4. 关注列表的 operation 是 `Following`，重放返回 200、一页 50 个用户并带下一页游标，
   `collectUsers()` / `readCursor()` 的解析逻辑已按真实响应验证过。
5. 自己的 userId 在 `twid` cookie 里（格式 `u=<19位数字>`），和 `Following` 请求
   variables 里的 userId 一致。所以 **不需要任何模板就能拿到自己的 id**。

顺带一个反面教材：用 DOM 抓关注列表只能拿到当时渲染出来的那几个（实测 7 个），
而接口一页就返回 50 个。这是「别抓 DOM」最直观的证据。

一个测试暴露的设计问题：请求**必须在 x.com 页面上下文里发**。从 service worker
直接 fetch，Origin 是 `chrome-extension://`，大概率被拒。所以 `xapi.js` 改成用
`chrome.scripting.executeScript({ world: 'MAIN' })` 把 fetch 注入页面执行——
和实测通过的路径完全一致。优先复用你已经开着的 x.com 标签页；一个都没有时才
自己开一个最小化的独立窗口，用完即关。这里不需要页面渲染，所以后台窗口
被挂起渲染完全不影响。

## 自动捕获（bootstrap）

模板没捕到时，扩展自己开一个后台窗口走一遍会触发对应请求的页面：

| 页面 | 捕获到的 operation | 实测耗时 |
|---|---|---|
| `/<handle>` | `UserByScreenName`、`UserOriginalsTimeline` | 导航后 2 秒内 |
| `/<handle>/following` | `Following` | 导航后 2 秒内 |

三个坑（都踩过了）：

1. **读 handle 必须指定标签页**。原来用 `ensureTab()`，它会优先复用你已经开着的
   任意 x.com 标签页，读的根本不是刚开的那个——读不到就误报「凭证失效」，
   表现正是「开了窗口又关了，什么都没发生」。
2. **`waitForLoad` 要先查当前状态**。导航可能在挂上 `onUpdated` 监听之前就完成了，
   只等事件会一直等到超时。
3. **不要固定 sleep 去赌请求发完**，改成轮询等模板落盘（超时 15 秒）。
   实测 2 秒就够，但这取决于网络，不该写死。

handle 读不到时的退路：用 `twid` 里的 userId 跳 `/i/user/<id>`，X 会 302 到
`/<handle>`，再从地址栏反推。

失败时会明确说清楚哪个 operation 没抓到，而不是静悄悄关窗。

**它是自动跑的，不是挂在界面上等你点。** 模板缺失本来就能自愈，
做成一个红色报错让用户去点是设计错误。现在：

- 装好 / 浏览器启动时（`onInstalled` / `onStartup`）就先准备好
- 面板和 popup 一打开也会调 `ensureReady`，缺了就自己补
- 界面上显示成中性蓝的「正在自动准备」，不是红色报错——它不需要你处理
- 只有 `auth` / `stale` 才红着提示，因为那两种自动开窗也解决不了，
  必须你本人去刷 x.com

三道闸防止反复开后台窗口：后台互斥锁、10 分钟节流、
以及页面内的 `tried` 标记。最后这道不能省——`selfHeal` 的回调会重绘界面，
重绘又会触发 `selfHeal`，没有它就是一个无限互发消息的死循环。

## 批次与断点续传

**只保留一个批次。** 一个批次 = 一次「把当前该抓的博主抓完」的任务，带一条待办队列：

```
batch = { id, status, queue:[还没抓的handle], doneHandles:[], posts:{id→tweet}, failures }
```

**每抓完一个博主就把队列和帖子落盘**（`runDigest` 循环末尾的 `set(K.BATCH, batch)`）。
断点就落在这里。所以中途取消、service worker 被回收、甚至浏览器重启，
下次点「继续抓取」都从队列头接着跑，不会重头再来。

- 超过 20 小时还没跑完的批次视为过期，下次会开新的（`BATCH_MAX_AGE`）
- `posts` 是 id→tweet 的 map，续传时天然去重
- **中途取消不写 `reported`**——否则续传时这批帖子会被自己的去重逻辑滤掉
- 「重开批次」只丢队列和帖子，不碰结论

**历史批次不留**：帖子体积大，留着会把 storage 撑爆。
**但 Grok 结论单独存**在 `digests` 里（保留最近 20 条），跟批次解耦——
批次滚掉了结论还在，面板上有「历史结论」折叠区。

## 任务互斥

后台同一时刻只跑一个任务（`background.js` 的 `withJob`）。这不是为了界面好看：
抓取、导入、捕获参数**共用同一个 x.com 标签页**（`xapi.js` 的 `ownTabId`），
并发时先结束的那个会 `releaseTab()` 把另一个正在用的标签页关掉，
后者就以「注入失败」告终。锁必须在后台，UI 遮罩只是把这个状态如实反映出来。

定时任务同样受锁约束，不会在你手动操作时插队。被锁挡下的请求返回
`{ busy: true }`，界面提示「等它跑完再操作」而不是报错——那不是失败。

任务进度通过 `jobState` 广播推给面板和 popup；面板每次打开还会主动问一次
`jobStatus`，因为后台可能正跑着定时任务。

## 按更新频率分档

`src/cadence.js`。每次抓完，用这批帖子自身的时间跨度算发帖密度
（抓 60 条可能覆盖 2 天也可能覆盖 60 天，所以不能除以固定天数），
EWMA 平滑后归档：

| 档 | 判定 | 抓取频率 | 每次条数 |
|---|---|---|---|
| 高频 | ≥ 3 帖/天 | 每天 | 60 |
| 常规 | ≥ 0.5 帖/天 | 每天 | 30 |
| 低频 | ≥ 0.1 帖/天 | 每 3 天 | 30 |
| 沉寂 | < 0.1 帖/天 | 每 7 天 | 40 |

低频档跳过的那几天不会漏帖：回看窗口会自动拉长到覆盖上次抓取以来的整段空档
（`lookbackSince()`），再配合 `reported` 集合做跨轮去重。手动点「立即汇总一次」
时无视档位，全部抓一遍。

## 已知风险

- **风控**：用自己的 Cookie 做自动化请求属于 ToS 灰区。默认配置已经很保守
  （每天一次，博主之间随机 2–5 秒间隔），不要改激进，也不要分发。
- **限流**：时间线端点有 15 分钟窗口限额。几十个博主一天一轮远在安全区内。

## Grok 总结（实测，2026-09-16）

把帖子交给 **x.com 自带的 Grok** 出结论。免费，不需要任何 API key。

**抓取和分析是两个独立任务**，这一点很重要：

- 「立即汇总一次」只抓帖子，**不会自动分析**。所以它可以随时取消，
  取消后已抓到的帖子照常保留。
- 「用 Grok 分析」单独对**已保留的那批帖子**跑，不重新抓取，可以反复重跑。
  抓了半天的数据不会因为分析失败就白费。
- 只有定时任务跑完会自动分析（`autoGrok` 设置，默认开）。
- 分析中点取消会立刻放弃等待 Grok 的响应（`grok.abort()`），不用干等到超时。

prompt 让 Grok **从这批帖子里挑 10 条最值得借鉴来涨粉的**，按潜力排序，
每条给出：一句话概括、值得借鉴的点（为什么它能拿到这些互动）、
一条可直接发布的 140 字正文、以及预期会吸引什么样的人关注。

明确要求它排除纯个人动态、圈内玩梗、需要大量前置背景的内容——
那些互动再高也不适合一个还在涨粉阶段的账号切入。

结论单独一区显示在面板顶部，带「复制全文」和「历史结论」折叠区。
没分析过时这一区就是入口，显示「当前批次已保留 N 条帖子，还没让 Grok 分析过」。

**直接伪造请求走不通。** `grok.x.com/2/grok/add_response.json`、
`x.com/i/api/2/grok/add_response.json`、`api.x.com/2/grok/add_response.json`
三个路径实测全部 `404 code 34`，缺的是 `x-client-transaction-id`——那个值是
X 前端每条请求现算的，伪造不了。注意这和抓帖子那条路结论相反：GraphQL 的 GET
端点不需要它，Grok 这个新端点需要。

**走得通的方式**：驱动 Grok 自己的输入框，让 X 的代码把请求发出去。
- `bsk fill` / 普通 `click` 都无效——React 受控组件不认 DOM 层面的赋值。
  必须用 `HTMLTextAreaElement.prototype` 上的 native setter 写 `value`，
  再派发 `input` 事件。
- 提交按钮只有 `aria-label="Grok something"`，没有文本也没有 `data-testid`。
- 答案不读 DOM，由 net-hook 截 `add_response.json` 的响应流。

**响应流格式**（实测抓到的真实数据）：

```
{"result":{"message":"Thinking about your request","isThinking":true,"messageTag":"header"}}
{"result":{"message":"正在生成五个字的回复","isThinking":true,"messageTag":"header"}}
{"result":{"messageTag":"response_start"}}
{"result":{"message":"好","messageTag":"final"}}
{"result":{"message":"的","messageTag":"final"}}
{"result":{"isSoftStop":true}}
```

答案 = `messageTag === 'final'` 的 `message` 拼接。**不能无差别拼所有 message**——
思考提示也带 `message` 字段而且是中文，会直接污染结论。

**驱动时每一步都要确认，不能想当然。** 最初的写法是
「设值 → `setTimeout(300)` → 点按钮」，结果在最小化窗口里超时失败：定时器被钳制、
React 还没提交重渲染，点到的是仍然禁用的按钮，什么都不会发生，
外面却只能干等到超时，报出「Grok 超时未返回」——完全误导。

现在 `drive()` 分四步，每步都有确认（实测数据）：

| 步骤 | 做法 | 失败时的报错 |
|---|---|---|
| 等输入框挂载 | 轮询 `textarea`，最多 20 秒 | 「Grok 输入框一直没出现」 |
| 写入 prompt | native setter + `input` 事件 | — |
| 等按钮可用 | 轮询 `aria-label="Grok something"` 且未禁用，最多 15 秒 | 「等了 15 秒，发送按钮始终不可用」 |
| 确认已提交 | 发送后输入框会清空、该按钮会消失（换成 Regenerate / Copy text），满足任一即可 | 「点了发送但输入框没清空」 |

这样「没发出去」和「发出去了但没截到回答」是两条不同的报错，不会混成一个超时。

**答案有两条通路，谁先拿到用谁。** 只靠流截取出过一次事故：
会话建好了、Grok 也答了（URL 上有 `?conversation=...`，页面上答案完整），
扩展却报超时。流截取依赖 net-hook 在 `document_start` 抢在 X 的 bundle
之前打上补丁，这个前提在某些时序下不成立。

- **通路一**：net-hook 截 `add_response.json` 的响应流。
- **通路二**：轮询页面 DOM，用 **prompt 锚定**——页面全文里我们发出去的
  最后一行之后的部分就是回答。不依赖任何 class 名或 `data-testid`
  （Grok 页面上只有 `primaryColumn` 有 testid，答案区什么都没有）。
  连续两轮文本不变才算写完。

**完成信号不能用「文本稳定」判断。** 这一点栽过一次：生成完成前，
页面上是逐字打出来的「Thinking about your request」和「Quick Answer」，
这两行能稳定好几秒不变，于是被「连续两轮不变」的规则当成最终答案采纳了——
用户拿到的结论就是那两行字。

真正的完成信号是按钮：**生成完毕才会出现 `Regenerate` / `Copy text` / `Share`**，
生成期间一个都没有。实测：

```
   2s  done=false   0 字   ← 思考阶段的占位文案已被过滤干净
   5s  done=false   0 字
   8s  done=false 250 字   ← 正在写，不采纳
  11s  done=false 613 字
  14s  done=TRUE  839 字   ← 采纳
  37s（另一次长回答）Regenerate|Copy text|Share 出现
```

`readAnswer()` 还要按行剔掉控件文案（`Quick Answer` `Auto` `Think Harder`
`Regenerate` `Copy text` `Share` `New Chat` `Stop`）。
注意「Thinking about your request」是**逐字打出来**的，只能按前缀匹配剔除，
精确匹配会漏掉 `T` / `Th` / `Thinking a` 这些中间态。

文本稳定性只留作兜底（万一 X 改了那几个 aria-label）：要求连续 5 轮
（15 秒）不变**且至少 200 字**——思考阶段那句占位文案只有二三十字，进不来。

实测轮询曲线（40 条帖子的 prompt）：

```
  5s     4 字        24s  1035 字
 11s   106 字        34s  1710 字 ← 写完
 18s   565 字        40s  1710 字（连续 2 轮未变 → 采纳）
```

轮询还顺带修掉一个隐患：**MV3 的 service worker 空闲 30 秒就被回收**，
而这里要等 40 秒以上。每 3 秒调一次 `chrome.scripting` 会重置那个空闲计时器，
worker 不会在等待中途被杀。

结论里会标明这次是「截自响应流」还是「读自页面」，以及耗时。

**结论里的编号是可点的。** Grok 的回答每条以「31 @handle 概括……」开头，
31 就是 prompt 里的序号。分析时把「序号 → 原帖 URL」的映射
（`grok.buildIndex()`）跟结论一起存进 `digests`，渲染时据此把编号还原成
指向原帖的链接，`@handle` 链到主页。**序号必须当成可选的。** Grok 时而输出「31 @handle 概括」，时而直接以
「@handle」开头一行、概括另起一行，还出现过「#7. @handle」。
正则写死成「数字 + @作者」就会整批漏掉，表现是只有主页链接、没有帖子链接。
现在序号可选（`#`、`.`、`、`、`)` 等修饰也都认），没序号时靠 @作者 定位。
prompt 里也加了一句明确要求保留原始编号，但不依赖它。

定位原帖是三级回退：

1. **序号 → index 映射**（分析时存下的，最准）
2. **index 里按 @作者 找** —— 序号对不上时兜底（Grok 有时会重排编号）
3. **当前批次里按 @作者 找** —— 救老记录，它们根本没有 index

三级都落空才不渲染链接，而不是渲染一个坏链接。

**注意一个固有限制**：Grok 不给序号时只能按作者定位，
如果同一批次里这个作者有多条帖子，链到的是最新那条，未必是它引用的那条。
序号存在时没有这个问题。

每条除了可点的编号，末尾还有一个明确的「原帖 ↗」—— 一个小小的 `#31`
太不显眼，实际用的时候定位不到。

渲染全程用 DOM 拼，不碰 `innerHTML`——正文是模型输出，不能当 HTML 塞进页面。

**顺带修的**：`net-hook` 取 URL 时只认字符串和 `Request`（`.url`），
漏了 `URL` 对象（只有 `.href`）。失败也盖上时间戳了——
之前界面上分不清是刚失败的还是上次遗留的。

**超时时长**：实测 40 条帖子的 prompt（6600 字），Grok **41 秒**生成完 2048 字。
原来 90 秒的上限其实够用——所以那次失败根本不是生成太慢。现在放到 180 秒，
超时只在真出问题时触发。

**后台窗口能不能跑**：能。渲染挂起的本质是 rAF 不再触发，实测把
`requestAnimationFrame` 打成永不回调（rAF 被调用 4 次，一次都没执行），
